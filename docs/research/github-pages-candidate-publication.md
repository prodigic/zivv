# Exact candidate publication on GitHub Pages

Primary-source research checked October 14, 2026 for #35 and #36. This note proposes a publication boundary; it does not implement publication, select a runtime, change credentials, or activate automation.

## Verified repository facts

- The [current production workflow](../../.github/workflows/deploy.yml) builds Vite output, uploads `dist`, and deploys on main pushes. Its concurrency group is `pages`, with `cancel-in-progress: false`. A candidate publisher must upload captured bytes rather than rerun this build.
- The [recorded preview checkpoint](../github-pages-preview.md) uses public `prodigic/zivv-test`, branch `gh-pages`, root publishing, and `/zivv-test/`. That document excludes **all recovery snapshots**, raw sources, private reports, databases, journals and keys from the preview repository. Its observed artifact commit is `66f03ba5f110b71c02e6d55284325a88d3cd11d4`; this research did not query current hosting settings.
- [Candidate identity](../../src/lib/ingestion/release-candidate.ts) hashes the normalized base path, public inventories and build provenance. The [publication reader](../../src/lib/ingestion/reviewed-candidate.ts) requires a trusted candidate ID, expected source commit, base path and build purpose. A preview-purpose `/zivv-test/` build cannot become a release-purpose `/zivv/` candidate by copying or editing files.
- [Candidate bundle verification](../../src/lib/ingestion/candidate-bundle.ts) authenticates the paired snapshot and returns checked public buffers. [Shared-ledger policy](../shared-ledger.md) permits encrypted ledger snapshots in source-repository Git history outside `public/`; clear ledgers and keys remain private.
- The [approved plan](../friday-delivery-plan.md) requires exact validated publication, live verification before acknowledgement, public-only rollback, preserved manual importing, and full private recovery. [Stage contracts](../weekly-stage-contracts.md) require stale-owner fencing and prohibit acknowledgement commits from causing an uncontrolled second deployment.

## Verified GitHub behavior

- A reviewed workflow can accept `workflow_dispatch` inputs; the workflow must exist on the default branch. Dispatch selects a workflow branch/tag independently of the payload SHA supplied as an input. Fine-grained dispatch credentials require `Actions: write`. [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch), [dispatch API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event).
- Custom Pages workflows can upload an existing directory and deploy it without a build. Deployment requires `pages: write`, `id-token: write`, and an environment such as `github-pages`. Pages settings do not associate the site with one exclusive workflow, allowing an additive workflow alongside the manual path. [Custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [publishing-source configuration](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).
- `upload-pages-artifact@v3` packages the requested directory, explicitly dereferences symbolic/hard links, and defaults artifact retention to one day. Therefore reject linked files and validate the exact allowlist before uploading; ephemeral Actions artifacts are transport, not durable rollback storage. [Versioned action source](https://raw.githubusercontent.com/actions/upload-pages-artifact/v3/action.yml).
- `deploy-pages@v4` selects the named artifact from its workflow run and submits its artifact ID. Its build version comes from the workflow's `GITHUB_SHA`, not an independently checked-out candidate payload SHA. Record both identities explicitly. [Deployment implementation](https://raw.githubusercontent.com/actions/deploy-pages/v4/src/internal/deployment.js), [API client](https://raw.githubusercontent.com/actions/deploy-pages/v4/src/internal/api-client.js), [runtime context](https://raw.githubusercontent.com/actions/deploy-pages/v4/src/internal/context.js).
- Concurrency serializes runs/jobs, but queue order is not guaranteed to follow dispatch order. Git-reference updates with `force: false` enforce fast-forward ancestry; their API has no separate expected-old-SHA parameter. Neither feature alone is a destination fencing protocol. [Concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [reference API](https://docs.github.com/en/rest/git/refs#update-a-reference).
- Branch-based Pages publishing supports `/` or `/docs`, not `/site`. Commits pushed with a workflow's `GITHUB_TOKEN` do not trigger branch-based Pages builds. Explicit dispatch avoids dependence on push-trigger behavior. [Publishing sources](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

## Recommended additive design

The following is an inferred design using those contracts, not an implemented guarantee.

1. **Persist immutable payloads before dispatch.** Use a non-served artifact branch in `prodigic/zivv` with `site/` containing only the private verifier's checked public buffers, `recovery/` containing only approved encrypted artifacts, and a public-safe candidate receipt. Bind the trusted candidate ID, public file hashes, source commit, ledger revision and encrypted snapshot hash to an immutable payload Git SHA. Construct raw Git blobs or recheck all bytes after checkout to reject line-ending/filter changes. Never put clear sources, journals, reports or keys in this branch; never copy recovery artifacts into `zivv-test`.
2. **Dispatch reviewed workflow code.** Add a default-branch publication workflow accepting payload SHA, trusted candidate ID, destination, request ID and expected prior promotion-control SHA. Fetch the exact payload SHA; run only reviewed verifier code, never scripts from the payload. Recheck public inventories and encrypted byte hashes against the privately verified receipt. The workflow does not receive a decryption key, rebuild assets, run ETL, or reconstruct the clear ledger. Upload only `site/` after rejecting missing, extra and linked files. Pin reviewed action implementations when implementing the workflow.
3. **Persist remote ownership of an in-flight promotion.** Under one destination concurrency boundary, compare the remote control head with the request's expected head. Append a control commit whose sole parent is that expected head and update the ref non-force. A competing head causes a conflict; stop rather than refetching and reparenting a stale request. Record candidate/payload/request identities and prior verified release in the in-flight record. Keep that ownership through deploy, live verification, acknowledgement or rollback. A subsequent job must first recover an unfinished in-flight record; job termination must not silently release its logical ownership. Restrict control-branch writes to this controller.
4. **Join the manual fallback at activation.** Preserve its build and operator entry points now. Before both paths become active, route manual deployment through the same remote controller and destination concurrency group. Merely sharing `pages` does not prevent an older request overwriting a newer release. Manual takeover must explicitly resolve or supersede the recorded in-flight operation.
5. **Acknowledge without another build.** Store deployment/verification receipts on a separate state branch. If published weekly status must also reach main, narrowly exclude acknowledgement-only changes from deployment; mixed application/public-data changes still follow the maintained manual path. Do not regenerate public output merely to acknowledge. Any necessary status-only public rebuild is a new validated candidate.

## Same release identity across staging and production

Keep the existing public `/zivv-test/` preview as a **routing-preview sibling** with its own identity. It remains useful for public preview and is not the exact release promotion gate.

Build and validate the immutable **release-purpose `/zivv/` candidate once**. In GitHub CI or locally, serve its exact `site/` buffers at `/zivv/` on a different origin, for example `http://127.0.0.1:4173/zivv/`, using a static path mount rather than rebuilding. Verify inventory bytes, deep links, current/future/weekly views and cached/fresh browser behavior there. Deploy those identical bytes and candidate ID to production afterward. No base rewriting, purpose change, or new custom-domain decision is required for this staging rehearsal. A public staging endpoint can be selected later without weakening identity requirements.

## Recovery and failure boundaries

- Persist publication intent and expected payload/control SHAs before remote writes. A crash after payload commit but before checkpoint is recovered by retrieving that exact SHA and verifying its inventory, not adopting whichever branch tip is newest.
- Dispatch/network uncertainty is recovered through the request identity and matching run/deployment receipts. Distinguish source-code SHA, payload SHA, workflow SHA, Actions artifact ID, Pages deployment ID and candidate ID; a successful push or workflow alone does not prove live publication.
- Live verification must compare the deployed manifest and required files with the exact candidate and exercise routes plus cached/fresh clients. Advance the publication cutoff only after a matching verification receipt.
- Rollback deploys the retained previous verified public bytes as a new deployment under the same controller. It preserves the newer private ledger and import history. If a newer promotion has legitimately superseded the failed one, an old rollback stops rather than overwriting it.
- Candidate recovery currently covers an encrypted logical ledger snapshot. Full activation still requires encrypted recovery of journal/artifacts, raw/prepared evidence, saved reports and frozen/configuration state, with a separately retained key. The public artifact branch must never contain those materials in clear form. See [current recovery limitation](../journaled-weekly-import.md).

## Authorization prerequisites and open choices

- A repository-scoped GitHub App or fine-grained token needs `Contents: write` for artifact publication and `Actions: write` for dispatch in each destination repository. The reviewed controller also needs narrowly scoped control-ref write authority. Deployment jobs use their repository token with the Pages/OIDC permissions above. Changing Pages source settings requires the relevant administrator/maintainer authority. Credentials, rulesets and environment policy remain activation prerequisites, not changes made by this note.
- Production already has an Actions publication path. Moving preview from branch publishing to an equivalent dispatch workflow is a separate configuration step; keep its working branch path until replacement is verified. Preview still receives public bytes only.
- Runtime, credential provisioning/renewal, full recovery-envelope format and independent monitoring remain deferred. No required environment approval is invented here; configure environment policy to match the already approved unattended release contract.
- Direct `gh-pages` publication is a simpler preview fallback, but root serving cannot hold a sibling `recovery/` privately and offers less explicit promotion control. Actions-artifact-only publication avoids a Git payload branch but expires and needs separate durable recovery storage. The non-served Git payload plus dispatch/controller approach best matches retained candidate identity and rollback needs.

Research performed through local source/document reads and official GitHub documentation/action source. No implementation, credential changes, production API calls or deployments were performed.
