# GitHub Pages deployment recovery

Verified 2026-10-14 against official GitHub documentation and action source. These are design findings; this research did not dispatch workflows or deploy Pages.

## Pages API contract

| Operation     | Contract                                                                                                                                                                                                        |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create        | `POST /repos/{owner}/{repo}/pages/deployments`; body `artifact_id` (number) or `artifact_url`, `pages_build_version` (string), `oidc_token` (Actions JWT), optional `environment` (defaults to `github-pages`). |
| Create result | HTTP 200 with `id`, `status_url`, `page_url`. The documentation does not constrain the deployment ID to a numeric ID or SHA.                                                                                    |
| Status        | `GET /repos/{owner}/{repo}/pages/deployments/{pages_deployment_id}`; HTTP 200 includes `status`; HTTP 404 is documented.                                                                                        |
| Cancel        | `POST /repos/{owner}/{repo}/pages/deployments/{pages_deployment_id}/cancel`; HTTP 204 or 404.                                                                                                                   |

Status/cancel accept a deployment ID or its commit SHA. The create example's `status_url` ends in `/status`, but the documented status endpoint and official action use the route above without that suffix. Use the documented route constructed from the returned ID. A build-version string is not documented as an idempotency key. [GitHub Pages REST contract](https://docs.github.com/en/rest/pages/pages?apiVersion=2022-11-28#create-a-github-pages-deployment), [official API client](https://github.com/actions/deploy-pages/blob/v4/src/internal/api-client.js).

The deploy job needs `pages: write` and `id-token: write`. GitHub Pages validates the job JWT's workflow/ref claims server-side. The official action requests the token using `core.getIDToken()`. A direct wrapper should request a fresh job token, pass it only in the request, and exclude it from logs and persisted state. [Official security/OIDC explanation](https://github.com/actions/deploy-pages#security-considerations), [token acquisition source](https://github.com/actions/deploy-pages/blob/v4/src/index.js).

## What can be recovered

There is no deployment-list operation in the documented Pages API. Classic `GET /repos/{owner}/{repo}/deployments` filters by `sha`, `ref`, `task`, and `environment`; it does not document filters or a Pages deployment mapping by `workflowRunId` or `artifactId`. Its arbitrary `payload` is not a documented correlation contract. Do not infer a Pages ID from a classic environment deployment ID. [Pages endpoint inventory](https://docs.github.com/en/rest/pages/pages), [classic deployments contract](https://docs.github.com/en/rest/deployments/deployments#list-deployments).

`actions/deploy-pages@v4` stores its Pages ID internally and logs it; its declared output is only `page_url`. It does not expose a durable deployment-ID output to the next workflow step. [Action metadata](https://github.com/actions/deploy-pages/blob/v4/action.yml), [creation and polling source](https://github.com/actions/deploy-pages/blob/v4/src/internal/deployment.js).

**Recommended wrapper design (inference):** persist the attempted create intent and its owner before POST, then persist the exact returned ID and artifact/run/attempt association immediately after receipt, before polling. A lost response or process death between server acceptance and persistence remains an uncertain create. Disable automatic POST retries and retain ownership; do not release the candidate or create again merely because the workflow failed. Commit-SHA lookup may help an operator investigate, but can identify the wrong same-SHA attempt and does not return an artifact/run identity sufficient for attribution. A 404 immediately after uncertainty is not proof that POST never committed.

**Recommended cancellation/recovery (inference):** with a known ID, request cancellation, then continue status checks until explicit terminal evidence. A cancellation 204 is acceptance, not proof that publication did not already win the race. Verify the production manifest/digest after `succeed` before claiming delivery. Keep ownership on transport errors, timeout, unknown status, missing attribution, or `deployment_lost` until an operator reconciles the external effect.

The v4 action recognizes `succeed`; final errors `deployment_failed`, `deployment_perms_error`, `deployment_content_failed`, `deployment_cancelled`, `deployment_lost`; temporary errors `unknown_status`, `not_found`, `deployment_attempt_error`. It continues polling other statuses. This is source behavior, not a complete public status enum. `deployment_lost` means final status was not reported, so treating it as proven no-publication would be unsafe. [v4 status handling](https://github.com/actions/deploy-pages/blob/v4/src/internal/deployment.js).

## Dispatch and workflow identity

`workflow_dispatch` accepts a branch or tag name as `ref`; the workflow must exist on the default branch. API version `2022-11-28` supports `return_run_details: true` and returns HTTP 200 with `workflow_run_id`, `run_url`, `html_url`; false returns 204. Version `2026-03-10` documents the run-details response directly. Use an explicit version and persist the response. [Dispatch API](https://docs.github.com/en/rest/actions/workflows?apiVersion=2022-11-28#create-a-workflow-dispatch-event), [current-version API](https://docs.github.com/en/rest/actions/workflows?apiVersion=2026-03-10#create-a-workflow-dispatch-event), [dispatch event prerequisites](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch).

**Recommended identity binding (inference):** dispatch a unique candidate tag whose target SHA was verified and which the publisher never moves. A tag is a valid ref, but the API does not make ordinary tags immutable. Verify the resulting run's `head_sha`, workflow identity, event, and attempt. Put a unique publish-attempt input in `run-name`; syntax allows the `inputs` context. Run-list filters include `event`, `head_sha`, and `created`, but no run-name or dispatch-input filter. Recovery therefore requires client-side matching of returned `display_title` plus SHA/workflow/event and rejecting zero/ambiguous matches; never select the latest run alone. Preserve the distinction between application publish-attempt identity and GitHub's `run_attempt`, which changes on reruns. [Run-name syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#run-name), [run retrieval/list fields](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28#list-workflow-runs-for-a-workflow).

`upload-pages-artifact` exports **`artifact_id`** (underscore), forwarding its nested uploader's `artifact-id`. Its pinned v3.0.1 composite still invokes `actions/upload-artifact@v4`, so pinning the outer action alone does not pin that transitive action. If all execution must be immutable, archive explicitly and invoke a separately verified, SHA-pinned uploader, or review/vendor the composite with its nested reference pinned. [Exact pinned artifact action](https://github.com/actions/upload-pages-artifact/blob/56afc609e74202658d3ffba0e8f6dda462b719fa/action.yml).

The candidate workflow selects the direct pinned `upload-artifact` option. Its output is **`artifact-id`** (hyphen), with separate `artifact-url` and `artifact-digest` outputs. Upload the prepared `artifact.tar` under the name `github-pages`, fail when absent, and retain it for one day to match the Pages composite's packaging/upload boundary. v4.6.2 is the newest v4 release shown in the official release inventory; newer major versions exist. [Exact uploader metadata](https://github.com/actions/upload-artifact/blob/ea165f8d65b6e75b540449e92b4886f43607fa02/action.yml), [release inventory](https://github.com/actions/upload-artifact/releases).
